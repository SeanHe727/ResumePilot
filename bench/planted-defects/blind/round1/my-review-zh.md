## 最重要的发现：其他组会把技术错误改写成「漂亮的正确句子」

我检查了各组给出的改写句，看其中有没有保留植入的技术错误（等于认可了这个错误，还替候选人润色了）：

- B：4 处。例如把「GRPO 每个 prompt 只采样 1 条 rollout」改写成「Stabilized sparse-reward GRPO training by using one scored rollout per prompt」；把「用动态批处理降低单请求延迟」原样润色；把「对嵌套模型做 Diebold-Mariano 检验」写成「Demonstrated statistically significant forecast improvement … using Diebold–Mariano」。
- D：3 处（动态批处理、Diebold-Mariano 等）。
- C：2 处（Diebold-Mariano；天气延误那条改成了「分开报告天气延误」，这一条其实算合理的改法）。
- A：0 处。A 不给整句改写，只指出问题。

这对候选人的伤害比「漏掉一个问题」更大：简历里原本的错误，被改写成一句看起来更专业、但依然错误的话，面试时会被懂行的人当场问住。

## 各组的优缺点

### A（ResumePilot）
优点：
- 找到的问题最全，写法和数据两类全部找到；叙事类靠程序算日期和核对技能，是其他组的两倍。
- 技术解释准确：Sharpe 应乘 √252、嵌套模型不能用 Diebold-Mariano、单条 rollout 无法计算组内相对优势，都说清了原因。
- 没有编造数字，也没有替错误的说法润色。

缺点：
1. 可执行性偏弱：大量建议是「Replace X with Y / Add Z」式的指令，很少给出改好的示范句。B / C / D 基本每条都给示范，候选人更容易直接照着改。
2. 优先级不稳定：ce 的「Top priorities」只有 1 条，而且是次要的「dashboard 职责式措辞」，比「GRPO 方法错误」「33% 算错」都不重要。
3. 仍有漏判和误判：
 - 动态批处理那条只要求「说明批处理的条件」，没指出「单请求用动态批处理不可能降低延迟」；C 直接指出了。
 - pm 的「What already works」把植入缺陷那一行（「conversion by 35%」，没有基线）当成优点，和它自己后面的建议互相矛盾。
 - 有少量把简历里不存在的东西当成问题（例如建议删除「性别和照片」，但简历里没有），也有少数过细的要求（例如教学评分要写出评分人数）。
4. 叙事上的判断偏软：quant 里插入的「面包店店长」整段，A 只说「保持简短，它和量化方向关系不大」，没有明确建议删掉或说明原因。
5. 建议条数多（27–32 条），读起来吃力。

### C（gpt-5.6-sol）
- 技术和数据判断最接近 A，而且表达直接（例如「交叉熵是损失函数，不是显著性指标」），每条都带示范改写。
- 叙事类很弱（2/6），会漏掉空档、没有证据的技能。
- 改写中有 2 处保留了技术错误。

### B（gpt-5.6-luna）
- 可读性好、结构清楚，但 quant 只找到 3 个。
- 改写中 4 处润色了技术错误；ce 里还建议把没有证据的 Kubernetes 放进技能栏，并编了一个 GitHub 链接。

### D（luna + skill）
- 格式建议多（技能分区、GitHub 优化），和这次的缺陷关系不大。
- 技术类只有 2/6，改写中 3 处保留了技术错误；上一轮还出现过编造数字（例如「adopted across 5 regions」）。

## 我的排序（主观）

| 简历 | 排序 | 主要理由 |
|---|---|---|
| ce | C > A > D > B | C 技术判断最准、表达清楚；A 覆盖最全，但漏了动态批处理、优先级失准；B / D 替错误润色 |
| pm | A > C > B > D | A 抓到了「改指标定义」和「自选择偏差」，C 其次；D 找到的最少 |

## 对 ResumePilot 的改进建议（按影响排序）

1. 每条建议附一句示范改写（仍然不得编造数字，缺的用占位符），解决可执行性问题。这是和其他组差距最大的地方。
2. 「Top priorities」固定取价值最高的 3 条，并优先放技术错误和数字错误。
3. 「What already works」不能选同时有问题的行。
4. 叙事类：对明显不相关的整段经历，要明确建议删掉或说明原因。
