# 架构分析报告：结构与接线

依据：`tmp/trace/421eb049-b67d-42b8-b832-9b121276e197/trace.jsonl`、`tmp/trace/conversation.md`、当前代码。本报告只谈**数据形状、层间契约和覆盖记账**；括号中是我的判断，不是模型内部 reasoning。

## 总结

```text
PDF → ResumeDocument（section → entry → bullet）
                   ↓ 渲染 ID 与内容
Main → Content / Wording / Narrative / Format
         └─ Content → Deep Research
                   ↓ 诊断写入 session
             generate_report → 报告 + coverage
```

本次主链跑通，但三处结构断点影响了结果：**Projects 没有形成 entry、agent 混用 entry/bullet ID、coverage 没把不可审内容和派发失败算进去**。补事实后的重评路径，以及解析入口的 trace，也还没在这次实测中闭合。

## 1. Projects：文字保留了，从属关系没建立

Project 和 Experience **共用 `ResumeEntry` 结构及 Content/Wording 审阅流程**，没有单独的 Project agent。此次脱敏 PDF 的实际结构是：

```text
PROJECTS
  entries: 0
  infoLines: 4       ← 两个项目标题、两个链接
  section bullets: 6 ← 六条 bullet 都在 section 下
```

因此没有“项目 A → 三条、项目 B → 三条”的机器可读关系，也没有项目 entry ID；Content/Wording 工具要求 entry ID，所以六条 bullet 未被逐条评分。Narrative 能看到文字并指出归属混乱，但不能把猜测的 3+3 当成解析结果。这份 fixture 的 `20XX` 日期和标题排版未触发开 entry 规则；Claude 报告真实简历在同一代码下能解析出两个项目 entry。（这是 fixture 暴露的结构脆弱点，不等于所有项目简历都会失败。）[标注规则](../src/document/row-labels.ts)、[组装](../src/document/assemble.ts)。

格式检查仍给 100 分、零 blocker。（“没有行丢失”不等于“项目与 bullet 的关系正确”。）

## 2. ID：已在共享 state，却没有安全地穿过每一层

解析后的 `state.resume` 已存 section、entry、bullet ID；不是缺一张共享 ID 表。问题是**模型只能看传给它的文本，工具只认自己契约里的 ID**：

- `renderResume` 会显示 entry 及其 bullet ID，却把 section-level bullet 渲染成无 ID 的 `- 文本`；项目标题只是 infoLine，也没有 entry ID。[渲染位置](../src/document/render.ts)
- Main 看到项目名字后，仍把名字填入 `review_content` / `review_wording` 的 `entryId`，四次均被拒绝。这里**没有可重试的正确项目 entry ID**；再次猜名字没有意义。[审阅工具](../src/tools/review.ts)
- Content 在第一条 Experience 下把 `s2:e0:b0` 等 bullet ID 填进 Deep Research 工具的 `entryId`，四次在启动子 agent 前失败；第二条改用 `s2:e1` 后三次成功。[深研工具](../src/tools/examine-depth.ts)

Deep Research 失败不是 Pydantic 问题：本项目是 TypeScript 工具 schema + 运行时查找。Content prompt 说“每行都有可寻址 ID”，工具描述却只写 `entryId: The entry being reviewed`，没有明确“传父 entry `s2:e0`，不是 bullet `s2:e0:b0`”。（仅改 prompt 可缓解，**改接口更可靠**：按 bullet 提问就接收 `bulletId`，由代码反查父 entry；工具名、字段名和示例都用模型无需猜测的词。）

## 3. Coverage：数字完整不代表内容完整

`coverage` 只统计解析出来的两个可审 Experience entry，于是得到 `eligibleEntries: 2, contentReviewed: 2, wordingReviewed: 2`。它没有表达六条未归属的项目 bullet，也没有表达四次项目派发失败。Main 的自然语言回复**本次有说明** Projects 未逐条审；但只读取结构化 coverage 的消费者会误以为“该审的都审了”。

应把“解析出但无法作为目标的内容”和“派发失败”列为显式账目；Main 在无合法 ID 时说明边界，而不是自由填写标题。必要时再设计 section-level 诊断入口，不能把 section bullet 偷算成已审 entry bullet。

## 4. Trace：内部链完整，两个入口仍在外面

Main → Content → `examine_technical_depth` → Deep Research → 网页搜索的父子记录完整；输入、输出和失败均可查，内部 reasoning 不记录。报告阶段 42 条 finding 形成 16 个报告点；2 个模型引用的 finding ID 不存在，被校验剔除。（内部 UUID 应保留；给模型短别名再映射回 UUID，可降低抄错概率。）

但脚本用 `app.start()` 在对话前解析 PDF，`parseFile()` 没把 trace 传给 `parse_resume`，且没有解析 span；因此仅靠 trace 看不到为何 Projects 没 entry。`/report` 等斜杠命令也在 Main span 之前直接执行。这两处是记录边界缺口，**不表示本次解析或命令本身失败**。[启动解析](../src/app.ts)、[命令分流](../src/agent/loop.ts)。

## 5. 补事实与局部重评：状态写入和判断更新是两步

回合 2 的 `800ms → 90ms` 已由 `record_fact` 写入 session，但旧诊断和报告没有自动刷新。即使简历原文没变，这个事实也可能改变对相关 bullet 的判断；重评时须明确标注它是**用户补充**，不是简历已写明。当前 Main 可见该事实，但专家是否收到它取决于 Main 是否填写 `supplied`；`generate_report` 本身不直接读取 `suppliedFacts`。[事实记录](../src/tools/working-state.ts)、[报告输入](../src/tools/generate-report.ts)。

不建议写穷举的 if/else 路由。给 Main 原则性授权更合适：*新事实或改写可能改变既有判断时，自行决定局部或全量重评，并说明重评范围与依据*；数据传递和目标合法性仍由工具保证。回合 3 用户称“已改写”却没有给新文字，Main 要求原文合理；所以本次脚本**没有测到真正的局部重评或报告更新**。
