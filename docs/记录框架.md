# ResumePilot Trace 记录框架

本文主要解释：**一次用户对话怎样被记录成可以重建的 agent 行为树**。Session、Audit、Memory 等原有记录只在最后说明它们与 Trace 的关系。

## 一句话理解

Trace 使用两种记录：

- **Span**：表示一段有开始、结束和父子关系的行为，例如一轮对话、一次工具调用、一个 specialist、一次模型请求。
- **Event**：表示 span 内发生的一件事，例如用户输入、模型请求、某次重试、工具返回或报告采用了哪些 finding。

最终每条记录写成一行 JSON，通过 `eventId` 和 `parentEventId` 还原成一棵树。

## 一次完整诊断的 Trace 形状

```text
Main turn span
├─ input：用户原话
├─ Query span：Main 的一次模型调用
│  ├─ input：prompt、messages、完整 tool schemas、模型参数
│  ├─ attempt 1：成功或失败
│  ├─ attempt 2：若发生重试
│  └─ result / failure：最终结果、usage、总次数
├─ Tool span：Main 调用 review_content
│  ├─ tool：模型给出的完整工具参数
│  ├─ decision：hook 拦截或改写（仅发生时记录）
│  ├─ Specialist span：Content Agent
│  │  ├─ dispatch：角色、briefing、工具权限、轮数、超时
│  │  ├─ Query span：Content 的模型调用
│  │  ├─ Inner-tool span：examine_technical_depth
│  │  │  ├─ tool：完整参数
│  │  │  ├─ Nested span：Deep Research
│  │  │  │  ├─ dispatch
│  │  │  │  ├─ Query span
│  │  │  │  └─ result
│  │  │  └─ result：Deep Research 返回给 Content 的内容
│  │  └─ result：Content 的结构化诊断
│  ├─ result：review_content 的原始结果
│  └─ decision：post-hook 改写后的结果（仅发生时记录）
├─ Tool span：其它 specialist / format / report
└─ span-end：本轮成功或失败、耗时

Report tool span
├─ findings collected：所有专家 finding 的 ID、角色和目标
├─ Query span：改进计划模型
├─ plan chosen：计划看过哪些 finding、选择了什么
├─ Query span：报告写作模型
└─ report points accepted
   ├─ reportPointId → sourceFindingIds
   ├─ unused：没有进入报告的 finding
   ├─ invented：模型引用了不存在的 finding ID
   ├─ unsourced：没有来源的报告点
   └─ unknownTargets：不存在的 entry 目标
```

## TraceEvent 的公共形状

```ts
TraceEvent {
  traceId
  eventId
  parentEventId?

  sessionId
  turn
  actor: {
    kind: 'main' | 'specialist' | 'nested' | 'system'
    id: string
  }

  phase:
    | 'span' | 'span-end'
    | 'input' | 'dispatch' | 'tool'
    | 'attempt' | 'decision'
    | 'result' | 'failure' | 'output'

  target?: { sectionId?, entryId?, bulletId? }
  purpose?
  tool?
  toolCallId?
  input?
  output?
  status?
  error?
  durationMs?
  usage?
  timestamp
}
```

`status: success` 只表示调用成功完成，不表示模型的判断正确。

## 1. Trace 怎样开启

Trace 在 App 组合根统一注入：

```text
未设置 RESUMEPILOT_TRACE_DIR
  → NoTrace
  → 所有插桩仍可调用，但不创建事件或文件

设置 RESUMEPILOT_TRACE_DIR=<目录>
  → 创建 run UUID
  → JsonlTraceWriter
  → RecordingTrace
  → 同一个 Trace 实例传给 Main、QueryEngine、SubAgent 和工具
```

文件位置：

```text
<RESUMEPILOT_TRACE_DIR>/<run-uuid>/trace.jsonl
```

入口代码：[app.ts](../src/app.ts)、[trace.ts](../src/trace/trace.ts)、[noop.ts](../src/trace/noop.ts)。

## 2. 父子关系怎样建立

`RecordingTrace.span()` 会：

1. 生成 span 的 `eventId`；
2. 立即写一条 `phase: span` 开启记录；
3. 把外层 span 的 `eventId` 写成自己的 `parentEventId`；
4. 使用 `AsyncLocalStorage` 把当前 span 传给内部异步调用；
5. body 返回或抛错时写 `phase: span-end`，包含状态和耗时。

因此 Content 和 Wording 即使未来并发执行，也会继承各自的父 span，不靠 JSONL 中的相邻顺序猜关系。

如果进程被 `kill -9`，最后一个 span 可能只有开启记录、没有 `span-end`；这本身可以作为“不完整运行”的信号。

## 3. Main Agent 记录什么

每条非命令用户输入开启一个 Main turn span：

```text
actor = { kind: 'main', id: 'main-agent' }
sessionId = 当前 session
turn = 当前对话轮次
```

span 内先记录用户原话，然后记录 Main 的模型调用和工具调用。Main 最终回复本身出现在 QueryEngine 的模型 `result` 中。

Main 工具调用记录两套输入/输出：

- 模型原本要求的参数；
- hook 真正批准并执行的参数（若有改写）；
- 工具原始返回；
- post-hook 最终交给模型的返回（若有改写）。

这样可以区分“模型选择错了”和“治理层改写后才变成这样”。入口：[agent/loop.ts](../src/agent/loop.ts)。

## 4. 所有模型调用怎样记录

所有模型请求都经过 `QueryEngine.query()`，所以只需在这里统一插桩：Main、所有 specialist、Deep Research、计划模型、报告模型和历史压缩模型都覆盖。

一次 Query span 记录：

```text
input
  task
  路由后的 model / provider
  systemPrompt
  messages（不含 reasoning）
  完整 ToolSchema[]
  maxTokens / jsonMode / effort
  cache 设置

attempt 1..n
  status
  error category / message / retryable / retryAfterMs
  durationMs

result 或 failure
  模型正文
  完整 tool calls：id / name / input
  usage
  attempts
  priorErrors
```

缓存命中记录为 `cached: true, attempts: 0`，因为没有真实请求。预算、路由和 provider 初始化阶段的失败分别用 `stage` 标明。入口：[engine.ts](../src/query-engine/engine.ts)。

## 5. Specialist 与 Deep Research 怎样记录

每个 SubAgent run 自己开 span。

`dispatch` 记录的不是泛化描述，而是这次实际边界：

- agent role 和名称；
- 实际 task 和 briefing；
- 必选、可选工具；
- context 中有哪些字段、允许哪些字段；
- `maxTurns` 和 `timeoutMs`。

内部每次模型调用由 QueryEngine 自动挂到这个 span 下。Specialist 调工具时，再开一个 tool span，记录完整 input/result。

Deep Research 使用同一个 `SubAgentRuntime`。当它从 specialist 的工具 span 内启动时，`actorFor()` 自动把它标成 `nested`，所以不需要针对 Deep Research 写特殊父子连接逻辑。入口：[sub-agent.ts](../src/agent/sub-agent.ts)。

这些内部工具**不走 Main 的 hook/audit 管线**：它们已处于一个被批准的 specialist 调用内部；Trace 只记录，不重新做权限、记忆和审计。

## 6. 报告来源链怎样记录

普通调用 trace 只能说明“专家说了什么”，不能说明“最终报告用了什么”。报告阶段另外记录三类 decision event：

```text
Specialist result
  ↓ everyFinding()
findings collected
  ↓ improvement-plan model
plan chosen
  ↓ report-writer model + ID 校验
report points accepted
```

每个报告点持有 `sourceFindingIds`。最后一条事件保存逐点 links，而不是只保存两张无法对应的 ID 清单。

目前 finding 使用内部 UUID。模型若抄错，引用会进入 `invented`，不会被当成有效来源。入口：[generate-report.ts](../src/tools/generate-report.ts)、[write-report.ts](../src/tools/write-report.ts)。

## 7. JSONL 怎样落盘

每个 event 独占一行：

```json
{"traceId":"…","eventId":"…","parentEventId":"…","actor":{"kind":"specialist","id":"content"},"phase":"dispatch","input":{},"timestamp":"…"}
```

Writer 的边界：

- run 目录权限 `0700`，文件 `0600`；
- UTF-8 实际字节计数；
- 单次上限 2 GiB，达到上限时尽量写一条停止说明；
- 新 run 开始时清理七天未更新的旧 trace；
- 只清理由 UUID 目录名和 `trace.jsonl` 两个证据共同确认的目录；
- 写入失败只在第一次向 stderr 告警，不能改变 agent 行为。

最后写盘前：

- key、authorization、token、secret、password、cookie 等字段替换为 `[redacted]`；
- reasoning、thinking、encrypted/opaque response items 替换为 `[reasoning omitted]`；
- 函数和 AbortSignal 不序列化。

入口：[writer.ts](../src/trace/writer.ts)。

## 8. 目前 Trace 没覆盖什么

1. App 启动时和 `/upload` 触发的 PDF 解析不在 Main turn span 内，也没有把 trace 传给 `parse_resume`。
2. `/report`、`/export`、`/new` 等斜杠命令在 Main 之前直接执行，不进入 trace。
3. 模型内部 reasoning 不记录；只能根据可见 prompt、tool call、结果和后续行为评审。
4. `tmp/trace/conversation.md` 是长对话测试脚本额外保存的文件，不是 trace writer 自动生成的。

因此当前 Trace 的准确范围是：**完整覆盖 agent 主链，尚未覆盖所有非 agent 入口。**

## 原有记录与 Full Trace 的关系

| 原有机制 | 记录目的 | 与 Full Trace 的差别 |
|---|---|---|
| Session / Checkpoint | 保存当前产品状态和恢复点 | 不解释状态怎样产生，也不保存完整逐字历史 |
| Audit | 记录 Main 工具权限决定及 200 字执行摘要 | 可治理、可快速查账，但不能重建；内部 agent 工具不进入 |
| `dispatch-trace` hook | 在终端显示 Main 给 specialist 的三项 briefing | 默认关闭、不落盘、无父子 ID、只覆盖部分 review 工具 |
| Metrics | 当前进程内统计 Main 工具耗时与成功率 | 只有汇总，进程结束即消失 |
| Memory | 保存跨 session 的少量用户画像与重复弱点 | 是产品记忆，不是执行历史 |

最简区分：

```text
Session：现在是什么
Audit：是否允许、是否成功
Trace：当时谁看到了什么，做了什么，结果怎样流到下一层和最终报告
```
